Design & Analysis of Algorithms — MST · Union-Find

How do you wire a country's cloud with the least fiber?

Every time a cloud provider opens a new data center, someone has to decide which cities to connect with physical fiber — and which routes to skip — so every site stays reachable at the lowest possible cost. That's not a metaphor. It's a Minimum Spanning Tree problem, solved with Kruskal's algorithm and a structure called Union-Find. Scroll down and run it yourself.

01 — The setup

Turn the map into a graph

Say a cloud provider needs to connect eight Indian data centers with dedicated fiber. Any two cities could be linked — but every kilometer of fiber costs money to lay and lease. The provider wants everyone connected, for the least total cost.

In algorithm terms, each data center is a node, each possible fiber route is an edge, and the cost of that route is the edge's weight. That's the whole translation — a real infrastructure decision, described as a weighted graph.

Think of it like planning roads between towns, not fiber. You don't need a road between every pair of towns — you just need enough roads that you can drive from any town to any other, and you'd rather not pay for roads you don't need.
Vocabulary, plainly
Node
A data center / city. A point that needs to be connected.
Edge
A possible fiber route between two data centers.
Weight
The cost of that specific route — distance, right-of-way fees, whatever the provider is minimizing.
Spanning Tree
A set of edges that connects every node, with no redundant loops — remove any edge and something becomes unreachable.
MST
The spanning tree whose edges add up to the lowest possible total cost.
02 — The goal

Connect everyone. Spend the least. Never build a loop.

A Minimum Spanning Tree is the cheapest possible way to keep a network fully connected. Two rules make it a tree rather than just "a bunch of cheap cables":

Rule 1 — Stay connected

Every data center must be reachable from every other one, directly or through other data centers. No site gets left off the network.

Rule 2 — No cycles

If a new cable would connect two data centers that already have a path between them, it's a redundant loop — extra spend with no new reachability. Skip it.

That second rule — "would this edge create a loop?" — is the exact question Kruskal's algorithm has to answer for every candidate cable, hundreds or thousands of times on a real network. Answering it fast is what Union-Find is for. Let's see it happen.

04 — Under the hood

    
Why Union-Find, specifically?

    
Every time Kruskal's algorithm looks at a candidate cable, it needs one yes/no answer: "are these two data centers already connected, even indirectly?" Checking that with a plain graph search would be slow if you did it for every single edge. Union-Find answers it in nearly constant time instead — using two small tricks.


    

      

        
1Union by rank

        
When merging two groups, always attach the smaller group under the larger one's root — never the other way around. This keeps the group's internal "depth" from growing unnecessarily, so tracing back to the root stays fast.

      

      

        
2Path compression

        
Every time you trace a node back to its group's root, reattach that node — and everyone you passed through — directly to the root. The next lookup for any of them is then instant.

      

    


    

      
What that buys you

      
With both tricks together, each find() or union() call runs in amortized O(α(n)) time — where α is the inverse Ackermann function, a number so small it's effectively 4 or 5 for any graph you could physically build. In practice: constant time. That's what makes Kruskal's algorithm run in O(E log E) overall — dominated entirely by sorting the candidate cables, not by checking for loops.

05 — Kruskal's vs. Prim's

    
Two routes to the same backbone

    
Both algorithms are greedy — they never reconsider a decision — and both guarantee the true minimum-cost network. They just build it up differently.

    

      
 Kruskal'sPrim's

      
        
ApproachSort every candidate cable by cost, add the cheapest one that doesn't create a loopGrow one connected region outward, always adding the cheapest cable leaving it

        
NeedsUnion-Find, to detect loops instantlyA priority queue, to find the next cheapest edge

Best suited forSparse networks — relatively few possible routesDense networks — many possible routes between sites

      
    

  







  

    
06 — Where the textbook model ends

    
One honest caveat

    
A real backbone provider — AWS, a telecom, anyone — almost never deploys a literal MST. An MST is, by definition, one cable cut away from splitting the network in half. Real infrastructure needs redundancy: if a single fiber line is dug up by construction equipment, the network shouldn't partition.

    
So in practice, MST is the starting point — the cost-optimal skeleton — which engineers then deliberately add extra edges to, often reaching for a k-connected topology (a network that survives k−1 simultaneous cable cuts). The algorithm doesn't disappear; it just becomes the cheap baseline you build resilience on top of, rather than the final architecture.
